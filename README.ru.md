# Аудит роста затрат Azure Databricks

Пошаговый метод (только чтение), чтобы **подтвердить, измерить и найти первопричину роста затрат, связанных с Azure Databricks**. Каждый промежуточный результат хранится в папке аудита, каждый шаг проверяется.

## Назначение и аудитория

Набор поддерживает аудит роста затрат Azure Databricks: от наблюдаемого роста до конкретных причин, у каждой из которых есть дата, измеренный эффект и владелец. Он рассчитан на специалистов, выполняющих такой аудит **впервые**: знание внутреннего устройства Databricks не предполагается, команды вводить не требуется. Термины определены в [словаре](reference/14_glossary.md) и подсвечиваются ссылками автоматически.

Набор только **читает** данные. Он ничего не изменяет в Azure и Databricks.

## Ход аудита

1. **Определить вопрос.** Какие месяцы, какая часть Azure, какая валюта, кто заказал.
2. **Скачать данные.** Одна большая выгрузка затрат из портала Azure и один небольшой отчёт для сверки. (По желанию приложение выполнит SQL в Databricks - только чтение.)
3. **Доказать, что рост настоящий,** и измерить его в сутки.
4. **Исключить учётные причины.** Закончившиеся скидки, новые покупки, изменения цен и курса поднимают счёт без роста потребления.
5. **Найти остаток:** сначала в Azure (сервисы, ресурсы), затем в Databricks (задачи, кластеры, warehouse).
6. **Найти причину** каждой крупной статьи: что изменилось, когда, сколько это объясняет.
7. **Сверить числа,** назвать владельца каждой причины и показать, что осталось необъяснённым.
8. **Независимая проверка,** затем написать отчёт с исправлениями и оповещениями.

Приложение хранит отдельную папку на каждый аудит, сохраняет все результаты и на каждом шаге сообщает, выполнено ли условие контрольной точки.

## Предварительные условия

- Компьютер с Python 3.10 или новее (остальное установит стартовый скрипт).
- **Доступ на чтение** к Azure Cost Management для подписок в охвате. Запросите его заранее: получение доступа обычно занимает больше всего времени. Точный список в [reference/02](reference/02_access_and_data_collection.md).
- По желанию: доступ на чтение к системным таблицам Databricks и SQL warehouse, чтобы приложение выполняло SQL за вас; Azure CLI для карты workspace; ключи IBM, если пользуетесь инструментами IBM.
- Трудозатраты: для первого аудита от одного до трёх рабочих дней, в зависимости от доступности данных.

## С чего начать

Весь плейбук проходится в локальном веб-интерфейсе - вводить команды не нужно.

```text
1. Дважды щёлкните run.cmd         (Windows; macOS / Linux: ./run.sh)
                                   первый запуск создаёт .venv и ставит requirements.txt
2. Откроется браузер http://127.0.0.1:8765
3. Аудиты → Новый аудит            создаёт audits\<id>\ с папками шагов, проверками и реестрами
4. Пройдите шаги 00 → 09           каждое действие - кнопка: загрузить выгрузку портала, запустить
                                   инструмент, выполнить / скопировать SQL Databricks, править реестр
                                   или документ, отметить проверки
```

Интерфейс: при запуске открывается **Документация**; вкладка **Аудиты** начинается с **управления аудитами** (создание, демо, удаление), затем список рабочих областей. Язык и тема - справа вверху. **Настройки** - подключение Databricks SQL и самопроверка инструментов.

Впервые сталкиваетесь с затратами Databricks? Сначала прочтите [reference/00_fundamentals.md](reference/00_fundamentals.md) (≈15 мин): из чего состоит счёт, DBU, формулы, обязательства, типичные причины роста.

## Что делает интерфейс на шаге

| Тип действия | Что происходит |
|---|---|
| Загрузка | Выгрузки портала (Cost Management, Cost Analysis) сохраняются в `exports/` шага под стандартным именем; добавляется строка доказательства |
| Инструмент | `tools/*.py` запускаются с уже подставленными выгрузкой и периодами аудита; результат в `results/`, добавляется строка доказательства |
| Расчёт | Сверка R6, размер роста + строка TOTAL моста, проверка направления R8, операционная Δ, остаток UNX, карточка драйвера, журнал воспроизведения, таблица моста |
| Databricks SQL | Запрос с параметрами из периодов аудита; **Выполнить в Databricks** (Statement Execution API, только чтение) или копировать + загрузить CSV |
| Реестр / документ | Табличный редактор CSV-реестров; markdown-редактор с предпросмотром для `scope_record.md`, заметок, карточек драйверов, отчёта |
| Проверки | Отметки `[x]` / `[-] причина` / `[!] ограничение`; статус шага, обязательные результаты и автоматические проверки данных обновляются сразу (`STATUS.md` перегенерируется) |

## Папка аудита

```text
audits/<id>/
  audit.json                 периоды, валюта, основная выгрузка (правятся в интерфейсе)
  STATUS.md                  перегенерируется интерфейсом после каждого изменения
  scope_record.md            живой документ: вопрос, охват, периоды, качество, размер, учёт, подписи
  evidence_register.csv      строка на каждый сохранённый результат (EVD-<шаг>-<nnn>)
  delta_bridge.csv           TOTAL Δ = учёт + первопричины + общие + вне охвата + необъяснённое
  hypothesis_register.csv    80 гипотез с тестами подтверждения / опровержения и статусом
  01_data_quality/ … 08_validation/   CHECKS.md, notes.md, exports/, results/
  06_root_cause/driver_<nn>_<name>.md      по одной на драйвер (действие 6.1)
  09_report_and_controls/findings_report.md
```

Имена результатов: `<id-sql-или-инструмента>__<детали>__<ГГГГММДД>.csv`, напр. `5.3_object_delta__B2026-02_C2026-04__20261109.csv` - интерфейс задаёт их сам.

## Принципы

- **Одна денежная истина:** деньгами считается реальный счёт Azure (Actual Cost) при неизменном охвате. Модель по прайсу Databricks, Amortized и отчёты IBM - вспомогательные взгляды, с ним их не складываем.
- **Сравниваем в сутки,** потому что в месяцах от 28 до 31 дня.
- **Причина, а не совпадение:** вывод получает статус `CONFIRMED`, только если рост виден в счёте, изменение датировано, цифры сходятся и опровергнуто другое объяснение (R9).
- **Объясняем не меньше 90 %,** остальное показываем открыто как `UNEXPLAINED`.
- **Только чтение:** ничто здесь не меняет ваш тенант. SQL расходует вычисления warehouse - получите согласие заранее.

## Требования

- Python 3.10+ (Windows: `py -3` или `python` в PATH). Доступ к PyPI при первом запуске (или заранее собранный `.venv`).
- Необязательно: Azure CLI (`az login`) для инвентаризации workspace (4.2) и входа в Databricks без токена.
- Необязательно: ID SQL warehouse + URL workspace, чтобы выполнять SQL из интерфейса.
- Сервер слушает только `127.0.0.1`. Порт: `set AUDIT_UI_PORT=8800` перед `run.cmd`.

Разработка: `python -m unittest discover -s tools/tests` - тесты инструментов и интерфейса (также **Настройки → Самопроверка**).
