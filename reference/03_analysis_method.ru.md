# 03 · Метод анализа - формулы и правила решений

<!-- plain -->
> **Обзор.** Формулы, на которых работает приложение, записанные в одном месте, чтобы любой мог их проверить: затраты в сутки, рост, день начала, объём против цены и как складывается мост дельты. Для работы в приложении это не обязательно, но нужно, чтобы объяснить число скептически настроенному коллеге.
<!-- /plain -->

Обозначения: **B** - базовый период, **C** - период сравнения, **P** - период устойчивости, `d(X)` = календарные дни в периоде X, `cost(X)` = итоговые затраты в X в одной валюте и одном регистре.

## 1. Размер изменения

| Метрика | Формула | Применение |
|---|---|---|
| Абсолютная месячная Δ | `cost(C) - cost(B)` | Влияние на бюджет конкретных месяцев |
| Ставка в сутки | `r(X) = cost(X) / d(X)` | Убирает эффект длины месяца |
| Δ в сутки | `Δr = r(C) - r(B)` | **Основная метрика размера** |
| Относительная Δ | `Δr / r(B)` (только если `r(B) > 0`) | Для коммуникации |
| Годовой эффект темпа | `Δr × 365` | Приоритизация |
| Устойчивость | `r(P) - r(C)` | ≈ 0 → ступенька сохранилась; ≈ -Δr → всплеск вернулся |
| Календарный эффект | `cost(C) - r(B) × d(C)` vs `cost(C) - cost(B)` | Показывает, сколько месячной Δ дало только число дней |

Длины месяцев 2026: янв 31, фев 28, мар 31, апр 30, май 31, июн 30, июл 31, авг 31, сен 30, окт 31. Неизменное потребление фев → мар даёт **+10,7%** помесячно.

## 2. Определение начала роста (правило R5)

Вход: суточный ряд затрат (Azure Actual по дням или модельная стоимость Databricks по дням).

1. Статистика базового периода B: `μ = mean(daily)`, `σ = stdev(daily)`.
2. Порог `T = μ + max(2σ, 0.10 × μ)`.
3. `m(d)` = скользящее 7-дневное среднее, заканчивающееся днём `d`.
4. **Начало** = первый `d` после B, такой что `m(d') > T` для всех `d' ∈ [d, d+13]`.
5. Если `m > T` менее 14 дней подряд → **всплеск** (записать начало/конец).
6. Недельная сезонность: 7-дневное среднее убирает влияние дней недели; если нагрузка в основном в будни, сравните также средние только по будням.

Реализовано в `tools/onset_detect.py` (действие 2.3) и `2.1_daily_cost_onset.sql`.

Интерпретация:
- Общее начало vs начало объекта (шаг 5.4): начало драйвера должно совпадать с общим (±2 дня), чтобы он был триггером; более позднее начало = дополнительный драйвер.
- Начало на границе месяца (1-го числа) → сначала подозревайте события биллинга/цены/обязательств/охвата, потом нагрузку.

## 3. Анализ вклада (одна группировка за раз)

Для ключа группировки `k` (сервис, счётчик, SKU, workspace, объект):

```
Δr_k        = r_k(C) - r_k(B)
share_k     = Δr_k / Δr_total               (может быть < 0 или > 100%)
coverage(n) = Σ_{top n positive} Δr_k / Δr_total
```

Правила:
- Ранжируйте по `Δr_k` (валюта/сутки), а не по % роста.
- Отрицательные вклады сохраняйте; для полной группировки должно выполняться `Σ Δr_k = Δr_total`.
- Никогда не смешивайте две группировки в одном водопаде.
- Существенность (R3): `|Δr_k| ≥ 0.05 × |Δr_total|` или топ-10 положительных.
- Класс изменения по ключу: `NEW` (`r_k(B)=0`), `GONE` (`r_k(C)=0`), `GROWN` (Δ > 0), `SHRUNK` (Δ < 0), `FLAT` (`|Δr_k| < 1% от r_k(B)`).

## 4. Разложение на объём и цену

Для одного счётчика/SKU с одной единицей:

```
Q = количество в сутки, p = фактическая цена за единицу = cost / quantity

Δcost = (Q_C - Q_B) × p_B        ← эффект объёма
      + (p_C - p_B) × Q_C        ← эффект цены
```

Точное тождество (без остатка). Для позиции `NEW` `p_B` := `p_C` → весь эффект в объёме. Эффект цены в модельной стоимости Databricks отражает только изменения **прайс-листа**; эффект выставленной цены берётся из `EffectivePrice` Azure (шаг 3.6).

**Эффект структуры** (несколько SKU с разными ценами, напр. jobs → all-purpose, classic → serverless): считайте объём/цену по каждому SKU, затем суммируйте. Перенос одной нагрузки между SKU выглядит как `GONE` на одном SKU + `NEW` на другом; взаимозачтите их в мосте и пометьте `MIX_SHIFT`.

Реализовано в `5.1_sku_volume_rate.sql`.

## 5. Разложение частота × стоимость запуска (нагрузки)

Для задачи, конвейера или warehouse:

```
cost/day = executions/day × cost/execution

Δcost = (n_C - n_B) × c_B       ← эффект частоты (больше запусков/обновлений/запросов)
      + (c_C - c_B) × n_C       ← эффект стоимости запуска (дольше, больше, повторы, больше данных)
```

Эффект стоимости запуска раскладывается дальше:
```
cost/execution = duration × (nodes or DBU/hour) × price
```
Используйте: длительность запуска (job_run_timeline), размер кластера (clusters SCD2), DBU/час (usage ÷ длительность).

Для задач реализовано в `6.01_job_cost_per_run.sql`.

## 6. Классические вычисления: согласованность DBU и VM

У классических нагрузок оба счётчика движутся вместе с узло-часами:
```
VM cost ≈ node_hours × VM price          DBU ≈ node_hours × DBU/node-hour
```
- Оба ↑ пропорционально → больше узло-часов (время работы/воркеры/простой).
- VM ↑ ≫ DBU ↑ → простаивающие инстансы пула, откат spot на on-demand, изменение цены VM/резервирования.
- DBU ↑ ≫ VM ↑ → смена уровня SKU (напр. jobs → all-purpose, Photon, Premium), переход на serverless.

## 7. Мост дельты

Мост - центральный артефакт аудита (`templates/delta_bridge.csv`).

```
TOTAL Δr (Azure Actual)
 ├─ ACCOUNTING      календарь | время покупки | кредиты | курс | охват | корректировки | выставленная цена
 ├─ ROOT_CAUSE      драйвер 1 … драйвер n   (статус CONFIRMED / LIKELY)
 ├─ SHARED_UNALLOCATED
 ├─ OUT_OF_SCOPE
 └─ UNEXPLAINED     = TOTAL - все строки выше
```

Правила:
- Суммы моста - в валюте **Azure Actual** в сутки. Если драйвер измерен по прайсу Databricks, пересчитайте по **наблюдаемому коэффициенту** корзины: `коэффициент = Δr Azure DBX_PLATFORM / модельная Δr DBX`, и запишите коэффициент как ограничение.
- Драйвер появляется в мосте один раз.
- `UNEXPLAINED ≤ 10%` (R4) или явное принятие.

## 8. Оценка доказательности (R9/R10)

| Статус | Требуется |
|---|---|
| `CONFIRMED` | (a) выставленная Δ в Azure Actual, (b) время изменения в пределах ±2 дней от начала драйвера, (c) количественно механизм объясняет ≥ 70% Δ драйвера, (d) опровергнута ≥ 1 альтернатива |
| `LIKELY` | (a) + (b) или (a) + (c) |
| `HYPOTHESIS` | Правдоподобно, не проверено; тест опровержения определён |
| `REJECTED` | Доказательства противоречат механизму в измеренном окне |
| `UNKNOWN` | Нет данных / срок хранения / нет доступа |

Одной лишь корреляции по времени для `CONFIRMED` никогда не достаточно.
