# 01 · Модель затрат - что выставляется, где и как связаны представления

<!-- plain -->
> **Обзор.** Более подробный взгляд на ту же картину, что и в основах: что именно выставляется, под какими счётчиками Azure это появляется и как соотносятся разные представления затрат (Actual, Amortized, модель Databricks, IBM). ## 1. Регистры и представления

| Представление | Что измеряет | Источник | Роль в аудите | Складывать с Azure Actual? |
|---|---|---|---|---|
| **Azure Actual Cost** | Выставленное потребление + покупки в выбранном охвате, без налогов, в валюте счёта | Cost Management → Cost analysis / Exports (Actual) | **Денежная истина** (R1) | - |
| Azure Amortized Cost | Те же начисления; покупки резервирований/savings plan распределены на срок действия | Cost analysis (Amortized) | Отделить время покупки от потребления | Нет |
| Выгрузка Azure FOCUS | Нормализованная схема с колонками billed/effective cost | Exports → FOCUS | Другая схема тех же начислений | Нет |
| Потребление Databricks | `system.billing.usage`: количество по SKU/единице, корректировки со знаком | Databricks SQL | **Анализ драйверов потребления** | Нет |
| Модельная стоимость Databricks | usage × `list_prices.pricing.effective_list.default` | Databricks SQL | Диагностический прокси по прайсу, без скидок | Нет |
| Дашборд использования / бюджеты Databricks | То же потребление, прайс-лист | Account console | Удобное представление | Нет |
| IBM Cloudability | Загруженная стоимость провайдера; скорректированные/амортизированные метрики; сопоставление; разделение затрат | Тенант IBM | Сверка, владение | Нет |
| IBM ApptioOne / TBM | Модельное финансовое распределение (пул → башня → приложение → BU) | Тенант IBM | Цепочка распределения | Нет |
| Счёт / договор | Итоговая проведённая сумма, налоги, поддержка, кредиты, обязательства | Финансы | Окончательный источник по оплаченной сумме | - |

## 2. Как нагрузка Databricks порождает начисления Azure

| Тип вычислений | Начисление DBU Azure Databricks | Начисление VM / дисков Azure | Где видна стоимость VM | Примечания |
|---|---|---|---|---|
| Классический all-purpose кластер | Да (`ALL_PURPOSE` / `INTERACTIVE`) | **Да, отдельно** | Managed RG workspace | DBU + VM - обе реальные, не дубли |
| Классический job-кластер | Да (`JOBS`) | **Да, отдельно** | Managed RG | Ставка DBU ниже, чем у all-purpose |
| Классический конвейер (DLT) | Да (`DLT`, уровень Core/Pro/Advanced) | **Да, отдельно** | Managed RG | |
| Classic / Pro SQL warehouse | Да (`SQL`) | **Да, отдельно** | Managed RG | |
| Простаивающие инстансы пула | **Нет DBU** во время простоя | **Да** | Managed RG | VM ↑ при неизменных DBU = сигнал пула/простоя |
| Serverless (jobs, notebooks, pipelines, SQL) | Да, ставка DBU выше | **Нет** (включено) | - | Никогда не добавлять гипотетическую стоимость VM |
| Model serving, Vector Search, Apps, Lakebase, AI functions | Единицы продукта (DBU, токены, часы) | Обычно нет | - | Единицы разных продуктов несравнимы |
| Управляемые функции (predictive optimization, мониторинг, FGAC) | Serverless DBU | Нет | - | Часто включаются незаметно на уровне аккаунта/каталога |
| Хранилище (ADLS/Blob) | Нет | Счётчики Storage | Аккаунты хранения клиента / корень DBFS в managed RG | Общее для продуктов |
| Сеть (egress, NAT, Private Link, firewall) | Возможны serverless networking SKU | Сетевые счётчики | RG VNet клиента | Общее; распределять только по доказательствам |
| Мониторинг (Log Analytics) | Нет | Счётчики Monitor | Цели настроек диагностики | Общее |

## 3. Иерархия детализации Azure vs иерархия Databricks

| Azure (выставлено) | Databricks (потребление) |
|---|---|
| Биллинговый аккаунт → профиль → подписка | Аккаунт |
| Группа ресурсов (вкл. managed RG) | Workspace |
| Service name → meter category → meter | `billing_origin_product` → `sku_name` → `usage_unit` |
| Resource ID | ID объекта в `usage_metadata` (job, cluster, warehouse, pipeline, endpoint, app, notebook) |
| Теги | `custom_tags`, `identity_metadata` |

Между иерархиями **нет ключа один к одному**. Мосты: workspace ↔ managed RG; теги кластера, передаваемые на VM (`ClusterId`, `ClusterName`, `Creator`, пользовательские теги); SKU ↔ имя счётчика Azure Databricks.

## 4. Тождества декомпозиции

```
Δ Azure Actual  = Σ учётных эффектов (покупка, кредит, курс, охват, корректировка, календарь)
                + Σ Δ операционных корзин (DBX_PLATFORM, DBX_CLASSIC_INFRA, STORAGE, NETWORK, MONITORING)
                + SHARED_UNALLOCATED + OUT_OF_SCOPE

Δ корзины       = Σ Δ объектов/драйверов + неатрибутированная Δ

Стоимость счётчика = количество × фактическая цена за единицу
Δ стоимости        = эффект объёма + эффект цены              (reference/03 §4)
```

## 5. Картина счётчиков → первая интерпретация

| Картина (B → C) | Наиболее вероятно | Не делайте вывод |
|---|---|---|
| DBU ↑ и классические VM ↑ | Больше классического времени работы: запуски, длительность, воркеры, простой | Что DBU и VM учитываются дважды |
| DBU ↑, VM без изменений | Рост serverless, управляемые функции, прайс/договорная цена | Что инфраструктура не используется |
| VM ↑, DBU без изменений | Простаивающие пулы, откат spot→on-demand, смена SKU VM, потеря покрытия резервированием, VM не от Databricks | Что простаивающие VM принадлежат Databricks без сопоставления RG/тегов |
| Транзакции хранилища ↑, объём без изменений | Больше листинга/мелких файлов, повторы, новые читатели, задачи оптимизации | Что хранится больше данных |
| Объём хранилища ↑ | Срок хранения, новые наборы данных, time travel / пропуски VACUUM, уровень репликации | |
| Сеть ↑ | Межрегиональные чтения, новый egress, трафик NAT/Private Link, обмен данными | Что все сетевые затраты от Databricks |
| Actual ↑, Amortized без изменений | Время покупки | Рост нагрузки |
| Модель ↑, Actual без изменений | Скидка, списание обязательства, несовпадение охвата | Ошибку в счёте |
| Число запросов ↑, стоимость warehouse без изменений | Попадания в кэш, параллелизм поглощён выделенной мощностью | Оплату за запрос |

## 6. Правила неаддитивности

1. Никогда не складывайте значения Azure Actual + модель Databricks + IBM.
2. Никогда не складывайте разные группировки одного регистра (подытог по сервисам + подытог по RG).
3. Никогда не суммируйте `usage_quantity` разных `usage_unit`.
4. Никогда не удаляйте отрицательные строки `RETRACTION` - они взаимозачитывают корректировки.
5. Никогда не суммируйте прямые + общие + распределённые затраты IBM, если модель не определяет их как непересекающиеся.
6. Actual и Amortized - два способа признания одних и тех же покупок.
