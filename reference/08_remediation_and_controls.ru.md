# 08 · Исправления и контроль (шаг 9)

<!-- plain -->
> **Обзор.** Что делать **после** аудита: как превратить каждый вывод в исправление с владельцем, как доказать экономию (замерить в реальном счёте не меньше 14 дней после изменения) и какие простые оповещения не дадут тому же росту вернуться незамеченным.
<!-- /plain -->

Исправления в аудите **предлагаются**, а выполняются только после согласования владельцем и вне аудита.

## 1. Порог исправления - обязателен для каждого предложения

| Поле | Содержание |
|---|---|
| ID драйвера / вывода | Из отчёта о выводах |
| Изменение | Точное изменение настройки / кода / расписания |
| Ожидаемая экономия | **Диапазон** в валюте/сутки и /год, выведенный из Δ драйвера и доли механизма |
| Риск | Влияние на SLA, задержку, свежесть, сбои, безопасность |
| Контрольная метрика | Что не должно ухудшиться (p95 длительности, доля успешных, свежесть данных, задержка дашбордов) |
| Откат | Как и как быстро |
| Владелец / согласующий | Названы |
| Проверка | Стоимость в сутки после изменения vs до, тем же методом (reference/03), ≥ 14 дней |

Экономия считается реализованной только после проверки на Azure Actual.

## 2. Типичные исправления по драйверам

| Драйвер | Варианты | Контрольная метрика |
|---|---|---|
| Простаивающие all-purpose кластеры | Автоотключение ≤ 30-60 мин через политику; shared-кластеры | Прерванные сессии |
| Избыточный размер кластеров | Подобрать воркеры/тип узла; диапазоны автомасштабирования | p95 длительности, OOM |
| Задачи на all-purpose вычислениях | Перенести на job-кластеры / serverless jobs | Время старта |
| Больше запусков | Вернуть/обосновать расписание; событийные триггеры с подавлением дребезга | SLA свежести |
| Более длинные запуски | Инкрементальная обработка, отсечение партиций, Photon, где выгодно | Корректность |
| Волны повторов | Max retries, оповещения о сбоях, устранение исходной ошибки | Восстановление |
| Continuous-конвейеры | Режим triggered, где позволяет задержка | SLA задержки |
| Full refresh | Убрать full refresh по расписанию | Корректность данных |
| Простаивающие пулы | Min idle 0 вне рабочих часов; более короткое автоотключение простоя | Холодный старт |
| Время работы SQL warehouse | Auto-stop 5-10 мин (serverless); ограничения размера/максимума кластеров | Задержка BI |
| Опрос из BI | Расписания дашбордов; кэширование; повторное использование результатов | Свежесть |
| Serving endpoints | Scale-to-zero (непрод); подбор пропускной способности | Задержка |
| Управляемые функции | Ограничить нужными каталогами; частота обновления | Польза функции |
| Объём хранилища | VACUUM / срок хранения; lifecycle-уровни | Time travel / восстановление |
| Транзакции хранилища | Уплотнение; меньше листинга | - |
| Межрегиональный трафик / egress | Размещать вычисления рядом с данными | Архитектура доступности |
| Приём логов | Категории диагностики, сэмплирование, срок хранения | Требования безопасности/аудита |
| Окончание обязательств | Продлить / изменить резервирования, DBCU | Финансовые обязательства |

## 3. Контроль после аудита

| Контроль | Механизм | Периодичность | Владелец |
|---|---|---|---|
| Бюджетные оповещения по Azure Actual | Бюджеты Azure Cost Management на охвате аудита; абсолютные + прогнозные пороги | Постоянно | FinOps |
| Бюджеты Databricks | Бюджеты account console по workspace / тегу | Постоянно | Платформа |
| Обзор крупнейших изменений | `tools/period_delta.py` (Δ/сутки в интерфейсе) последние 7 дней vs предыдущие 28; `5.3_object_delta.sql` | Еженедельно | Платформа + FinOps |
| Наблюдение за началом роста | `2.1_daily_cost_onset.sql` / `tools/onset_detect.py` за последние 90 дней | Еженедельно | Платформа |
| Политики вычислений | Политики кластеров (автоотключение, максимум воркеров, типы узлов, теги), стандарты warehouse | При изменениях | Платформа |
| Покрытие тегами | `5.5_attribution_coverage.sql` - цель: потребление без тегов < 5% | Ежемесячно | Платформа |
| Дрейф конфигурации | Новые кластеры/warehouse/конвейеры/endpoint и изменения размера (`6.06`, `6.09`, `5.6`) | Еженедельно | Платформа |
| Отслеживание обязательств | Календарь окончания RI/SP/DBCU/кредитов | Ежемесячно | Финансы |
| Ежемесячная сверка | Azure Actual vs Amortized vs модель Databricks (проверка направления R8) | Ежемесячно | FinOps |
