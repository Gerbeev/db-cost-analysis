# 04 · Ловушки и стоп-правила

<!-- plain -->
> **Обзор.** Условия, при которых результаты оказываются неверными без сообщения об ошибке: выгрузка, сделанная дважды, смешанные валюты, пропущенный месяц и т. д. Для каждой указано, как её заметить и что делать. Если приложение или проверки упоминают номер **STOP**, это страница с объяснением.
<!-- /plain -->

## 1. Стоп-правила - не считайте и не публикуйте дельты, пока это не исправлено

| ID | Условие | Как обнаружить | Как исправить |
|---|---|---|---|
| STOP-1 | Перекрывающиеся запуски выгрузки Azure / дописанные ежедневные снимки с начала месяца | Итог выгрузки > итог Cost Analysis; повторяющиеся даты в запуске | Один запуск на месяц, части объединяются один раз |
| STOP-2 | Смешанные валюты в одном ряду | > 1 значения валюты | Разделить ряды; явный мост пересчёта курса |
| STOP-3 | Пропущенный или неполный месяц | `1.1_usage_coverage.sql` days_with_data < days_in_month; пропуски дат в выгрузке | Перевыгрузить; или пометить `UNKNOWN` (никогда не ноль) |
| STOP-4 | Смешаны Actual и Amortized | `PricingModel`/метрика различаются между периодами | Перевыгрузить с одной метрикой |
| STOP-5 | Охват в B и C различается | Наборы подписок/workspace различаются | Исправить охват или показать изменение охвата как учётный эффект |
| STOP-6 | Неоднозначное соединение с прайсом | Дубли в `1.3_price_join_check.sql` > 0 | Исключить SKU из модельной стоимости (R7) |
| STOP-7 | Срок хранения не покрывает нужные даты | Самая ранняя строка системной таблицы > начала окна | Сократить окно или пометить `UNKNOWN` |
| STOP-8 | Включён текущий неполный месяц | Конец окна > последнего полного месяца | Исключить |

## 2. Ошибочные интерпретации, дающие ложные первопричины

| Ловушка | Почему неверно | Правильный подход |
|---|---|---|
| Сравнение месячных итогов фев vs мар | +10,7% только из-за числа дней | Ставки в сутки (reference/03 §1) |
| Ранжирование по % роста | Доминируют мелкие позиции | Ранжировать по Δ в валюте/сутки |
| Сложение подытогов по сервисам + RG + счётчикам | Одни и те же деньги трижды | Одна группировка на водопад |
| Сложение модельной стоимости Databricks с Azure Actual | Одни и те же DBU дважды (прайс vs счёт) | Раздельные регистры (R1) |
| Считать DBU и VM дублями | Классические вычисления выставляют оба | Атрибутировать раздельно |
| Добавлять стоимость VM к serverless | Serverless включает вычисления | Только DBU |
| Удаление отрицательных строк потребления | Корректировки удалены → завышенное потребление | Взаимозачитывать все `record_type` |
| Суммирование `usage_quantity` разных единиц | DBU + токены + ГБ бессмысленно | Группировать по `usage_unit` |
| «Пустой job_id = потери» | У all-purpose / SQL / платформы job_id нет по замыслу | Классифицировать как `CLUSTER`/`WAREHOUSE`/`UNATTRIBUTED` |
| Считать строки `job_run_timeline` запусками | Длинные запуски нарезаны по часам | Сворачивать по `workspace_id, job_id, run_id` |
| Считать строки serverless-потребления запусками | Несколько строк на запуск | `COUNT(DISTINCT job_run_id)` |
| Соединять задачи только по `job_id` | Уникален только в пределах workspace | Ключ = `workspace_id + job_id` |
| Соединение SCD2 без окна действия | Дублируются строки конфигурации | Последняя строка ≤ времени |
| «Новый SKU = новый ресурс» | Возможны переименование / переклассификация SKU | Проверить ID объектов и историю цен |
| «Новый ID в биллинге = новое развёртывание» | Пересозданный объект, ротация ID | Проверить первое изменение SCD2 и имя |
| Число запросов ↑ ⇒ стоимость ↑ | Warehouse оплачивается за время работы/размер, а не за запросы | Использовать события warehouse + потребление |
| Нет таблицы ⇒ нет нагрузки | Региональные / preview-таблицы | Пометить `UNKNOWN` |
| Managed RG = все затраты Databricks | Хранилище/сеть/мониторинг в других местах; возможны ресурсы не от DBX | Явно сопоставить зависимости |
| Нет оповещения об аномалии ⇒ нет всплеска | История оповещений пересчитывается; пороги зависят от представления | Независимо воспроизвести ряд затрат |
| Отчёт IBM ↑ ⇒ расходы Azure ↑ | Изменения сопоставления/распределения/модели двигают затраты без новых расходов | Проследить до источника (reference/06) |
| Корреляция по времени ⇒ причина | Совпадающие изменения обычны | Критерии R9 |
| Простой в месячном агрегате ⇒ удалить | Может быть нужен (SLA, streaming) | Порог исправлений (reference/08) |

## 3. Оговорки по типам данных

- `Date` в Azure - дата потребления; покупки могут быть датированы датой покупки, а не потребления.
- `CostInBillingCurrency` в Azure без налогов; кредиты в зависимости от договора могут быть вне cost details.
- `usage_date` в Databricks - UTC; суточное представление Cost Analysis может использовать другую границу суток - ожидайте сдвигов ±1 день на дате начала.
- `system.billing.usage` может пересчитываться спустя дни; записывайте время запуска запроса.
- `node_timeline` может не содержать узлы, жившие < ~10 минут.
- Покрытие `instance_events` не включает SQL warehouses; наблюдаемые часы пула - нижняя граница.
- Начальное состояние `warehouse_events` до окна может быть неизвестно.
- Прайс-лист не включает договорные скидки; соотношение модели и счёта может меняться при изменении обязательств.
